# What bots can reach (Docker installs)

In botdot's Docker image, botdot itself runs as root, the Chief of Staff as its own user, and **every bot as its own user**. Linux then enforces the boundaries on the botdot server, whatever tool a bot uses (Read, Bash, scripts). The account's computer, where bots with a computer work, is the exception: there every bot is the same user, with sudo (below).

| | botdot | Chief | A bot |
|---|---|---|---|
| botdot's data, the vault and its key, the Claude sign-in, Bitwarden | ✓ | – | – |
| The Docker socket (control of the machine) | ✓ | – | – |
| botdot's controls (create bots, settings, vault…) | ✓ | ✓ through its tools | – |
| Its own run's tools (memory, jobs, logins, apps, computer), with its own run key | | | ✓ |
| A bot's workspace | ✓ | read | its own only |
| The account's computer: every bot's files, screen, browser and programs there, and the secrets used there | ✓ | its state, logs and restart, through its tools | all of it, for every bot with a computer (as `box`, with sudo) |

- **Claude:** the Chief and bots get only the short-lived access token from botdot's own sign-in (never the refresh token); botdot renews the sign-in before it runs out.
- **Run keys, and what a bot is told** (its instructions, its notes, the shared notes and its chat), are in private files of that bot's own user, not on the command line, where every user could read them. The file with what it is told is removed when the run ends.
- **Through Tailscale from the machine itself** (which Tailscale would vouch for as you), botdot refuses requests: only your other devices use the tailnet address.
- **The account's computer is shared:** every bot with a computer works on the account's one computer as the same user, `box`, with sudo ([ADR 035](adr/035-the-account-has-one-computer-all-its-bots-work-on-with-sudo.md)). Each bot has a screen and browser of its own there (#105), but those are separate work surfaces, not walls: each bot can see, change and end what the others do, watch their screens, and read any saved login, card, identity or SSH key that botdot types or hands to a command there. botdot never writes such a secret to a file or puts it on a command line, and lends an SSH key through an ssh-agent that lives only as long as the one command. Turn on "Usable in its computer" only for a secret you accept every bot there can read: it was meant for secrets that guard something on that computer, and it is now also how a bot signs an API call with several secrets. A bot may use up to 8 logins in one command (`run_with_login` with `logins`, for an API that signs each request with several secrets), each in variables of its own (`BOTDOT_<NAME>_PASSWORD`); each of them needs "Usable in its computer", which you turn on one login at a time, and every bot there can read each one. One bot's runaway program can also use up the computer's memory, which is the account's share, and end another bot's. Other accounts, the botdot server and the machine stay out of its reach.
- **What an update and a reset keep:** an update of the computer to a newer desktop keeps `/home/box`, `/workspace`, the browsers' logins and the computer's Tailscale login, and loses what apt installed. A reset erases all of it, for every bot, after a confirmation; the Chief can only ask for one on a card in Needs you. A bot's old computer of its own, from before, stays stopped until you copy its files to `/workspace/<bot id>/old-computer` and erase it.
- **Programs on the computer:** a bot installs what you ask for with `sudo apt-get install`, or into the shared home with `botdot-install` (conda-forge, pip, npm). **The computer on your tailnet:** a bot can run `botdot-tailscale up` there, which puts the account's computer on your tailnet as one device once you open its login link and approve it ([#106](https://github.com/Kordal/bot-dot/issues/106)). It is one device for the whole computer, not one per bot: every bot on the computer uses it, through its proxy on `localhost:1055`, and can reach whatever your tailnet's access rules let that device reach. So give it a tag that limits it to what the bots need, and remove it in the admin console to cut it off. botdot runs it as root, in userspace, and starts it again with its saved login each time the computer starts. Its key and login are root's, which every bot is through sudo. No tailnet device can connect to the computer: Tailscale's shields are up, set again at each start, and botdot's firewall drops what Tailscale would hand on to botdot's control and screen ports, so they stay out of reach of the tailnet as of the local network. A bot with sudo could still open a port of its own to your tailnet. A bot's own Tailscale from its old computer, or from box's home, is not carried over: the computer joins as a new device, and you can remove the old ones in the admin console.
- **Who is asking:** botdot looks up which user opened each connection from the machine itself (any of its addresses). When it can't tell for sure, it refuses the request.
- **The Chief on the web:** the Chief searches the web and reads pages itself. Once it has in a chat, what it changes there (bots, jobs, skills, the Board, groups, reminders, settings) waits for your OK on a card that shows exactly what it sent ([ADR 033](adr/033-the-chief-reads-the-web-and-what-it-changes-after-waits.md)). Reading a page is not held, so an address it fetches could carry something out; its instructions forbid putting your data in one.
- **Connectors:** a bot with an app's connector can ask for any of that app's actions, writing ones too; a write waits for your OK on its card, unless you chose **Always allow this action** for it. What its main assignment says it should do is guidance, not a limit.
- Separate users on the botdot server are turned off with `BOT_DOT_SEPARATE_USERS=0`. On a Mac, everything runs as you, as before: a bot with Read or shell access can then read `data/memory.db` and the other bots' folders ([SECURITY.md](../SECURITY.md)).
