# ADR-007: Installed tools are pinned lists per bot, placed by a tools user

- **Status:** Accepted (2026-10-03, TOOL-001); amended by TOOL-008 (2026-10-03): a second way to place a tool's files, for a data folder that refuses micromamba's copy
- **Owning task:** TOOL-001

## Context

[Milestone 4](../product/milestone4.md) lets the Chief of Staff get a command-line tool installed on the botdot server for one bot, after the owner's OK on a card in Needs you. The owner chose: named tools without root, an OK for every install, a tool belongs to one bot, backups carry the list and not the files, and a tool outside the registry may come from a link.

Today nothing can install anything. The container drops its capabilities and sets `no-new-privileges`; the server runs as user 60000; the only root process, the privilege broker, accepts five fixed operations and starts nothing but Claude or bash as a bot (`lib/privilege-broker.js`). An update replaces everything outside the data folder.

A trial on 2026-10-03 ([milestone4-research.md](../archive/product/milestone4-research.md), "Uncertainties resolved at stage 4") ran three installers as user 60000 under the container's flags, on `linux/arm64` and emulated `linux/amd64`. All three worked without root. What decided between them, and what constrains the design:

- micromamba is one file of about 20 MB and reaches conda-forge, which has `gh`, `make`, `jq` and ffmpeg for both architectures.
- It installs from an explicit list (one URL with `#sha256:` per package) with no solver and no index download, in under a second for `gh`; a wrong hash aborts and installs nothing.
- Finding that list needs the solver once. For `gh` that run took 630 MB of memory, because micromamba fell back to the whole index.
- A bot's user can run a tool and cannot change it when only the top folder is given to the bot's group with mode 0750. That step needs root. A recursive change breaks other bots, because micromamba hard-links files from its cache into every folder.
- The folder's path must stay fixed: after a move ffmpeg lost its certificate checks.
- Only one package of the four tools brought an install script; `--skip-run-link-scripts` turns it off and the tool still works.
- On a Mac's bind mount micromamba's cache breaks the solver on its second run; an install from an explicit list works there.

## Decision

- **The registry is conda-forge, read with micromamba.** The image carries one micromamba binary per architecture, pinned by checksum in the `Dockerfile`. A tool is a conda-forge package named by the Chief; botdot adds no list of its own.
- **Resolve when asked, pin when approved.** When the Chief asks for a tool, botdot resolves the name once into an explicit list for the server's architecture: every package's URL and sha256. Nothing is installed. The card's version and download size come from that list, and its one-line description from the registry's record of the package. The owner approves that list. The install uses exactly it: no solver, `--skip-run-link-scripts`, `--always-copy`, `--safety-checks enabled --extra-safety-checks` (without `--always-copy` only the second way, below).
- **The list is the truth.** `tools.json` in the data folder holds, per bot and tool: the name, the version, the source (registry or link), the explicit list, who asked and when the owner approved. At start botdot makes each bot's folder match its list: it installs what is missing and removes what is not listed. A backup carries `tools.json` and skips the files.
- **One folder per bot, one prefix per tool.** `data/tools/<bot id>/<tool>/` holds the tool; `data/tools/<bot id>/bin/` holds links to the commands that the tool's own package brings, not to those of its dependencies. That `bin` is on the `PATH` of the bot's runs, script jobs and dashboard tile scripts, whether or not it is empty. The paths never change.
- **A tools user owns the files.** A new user (`botdot-tools`, UID 60400) owns everything under `data/tools`. A bot's folder belongs to the tools user with the bot's group and mode 0750 at the top only: the bot can run its tools, cannot write them, and no other bot can enter. The server's own user cannot write them either.
- **The broker installs, from data, not from a command.** The privilege broker gets three fixed operations: resolve a name (`toolResolve`), install a bot's tool from a list (`toolInstall`), remove what a bot no longer has (`toolRemove`). The caller sends the bot, the tool's name and the list; a list entry is an address under `https://conda.anaconda.org/conda-forge/` and a sha256, and anything else is refused. Root only makes the folders and sets the group on the bot's folder; a worker (`lib/tools-worker.js`) started as the tools user builds micromamba's command line and runs it, with an environment of four fixed names (`PATH`, `LANG`, `HOME`, `MAMBA_ROOT_PREFIX`) that holds no secret. The broker's rule stays: neither a root command nor an arbitrary chown is expressible.
- **The cache is not data.** micromamba's package cache and index, and the tools user's home, are in `/var/cache/botdot-tools` in the container's own filesystem, not in the data folder: they are gone after an update, are never backed up, and stay off a Mac's bind mount. The one exception is the second way of installing, which keeps a cache on the data folder for the length of one install.
- **Two ways to place a tool's files; the second only after the first was refused.** (TOOL-008.) The first way copies every file from the cache in the container onto the data folder (`--always-copy`). It is always tried first, and on a Docker volume, which a Linux botdot server has, it is the only one that runs. On a botdot server hosted on a Mac (`compose.mac.yaml`) the data folder is a bind mount of the Mac's disk, and that mount refuses micromamba's own copy: `filesystem error: cannot copy: Permission denied [<cache>/pkgs/…] [/data/tools/<bot>/<tool>/…]`, with the cache in the container and with the cache on the mount, while `cp` and `cp -p` of the same file onto the mount work (measured on 2026-10-03 as the tools user with the worker's environment and flags). When micromamba ends with that refusal, and only then, the worker removes the half-made folder and installs the same list once more without `--always-copy` and with `MAMBA_ROOT_PREFIX` at `data/tools/.cache`: micromamba then hard-links from a cache on the same mount, which worked there. The list, the checks, `--skip-run-link-scripts` and the environment of four names are the same; the tools user's home stays in the container.
  - **That cache lives for one install.** The worker removes `data/tools/.cache` when the install ends, whether it worked or not, and before any mode in the tool's folder is set; a cache that a stopped install left goes with the next install or removal, so at the latest when botdot starts. With the cache gone no file of a tool is linked to anything: not to a cache and not to another bot's tool, so the trial's trap (a change of mode or group on one bot's folder reaching every bot's files) cannot arise, the cache cannot grow, and nothing of it is ever in a backup, which skips `data/tools` anyway.
  - **Which way placed a tool is recorded:** `way` (`copy` or `links`) in the tool's `.botdot-tool.json`, and `way: "links"` on `tool.installed` in the audit log.
  - **Any other failure is not tried a second way:** a full disk, a wrong checksum and an unreachable registry end the install as before.
- **A bot's `bin` comes first on its `PATH`.** An installed tool that brings `git` or `python3` stands in for the botdot server's own, for that bot. Of two tools of one bot with a command of the same name, the one the owner approved later has it. Which commands a tool took over is known when it is installed, and the Chief is told with the result, so that it says so.
- **Resolving runs one at a time and is allowed its memory.** botdot asks micromamba (a dry run, as the tools user) once per ask, never two at once, and gives it five minutes. For most tools that takes about 100 MB; for a tool without dependencies micromamba falls back to the whole index (630 MB in the trial). An ask that cannot be resolved adds no card and says why; nothing else on the server is affected. The registry's own record of a package (its summary and latest version) is read by the server from `api.anaconda.org`, and only those fields are kept.
- **A restore onto another kind of processor keeps the version.** `tools.json` records the platform a list was resolved for. When it is not the server's, botdot resolves the same name and version again for this processor and installs that with no new OK. When the registry has no such version for it, the tool is not installed and the owner is told once; a different version is a new ask.
- **A tool that no longer starts is installed again.** At start botdot runs the first command of each listed tool with `--version`, as that tool's bot: a missing command, or one that cannot be started, is installed again from its list. Running it as the bot gives the check no more than the bot has. Each tool's folder records the list it was installed from; a folder made from another list than the one `tools.json` holds now (an older backup was restored) is removed and installed again from that list.
- **A tool from a link is one file, pinned by its checksum.** The tools user downloads the address over https, botdot records the sha256 and the size, and the card shows them. On Install the same file is fetched again and must match. A `.tar.gz` or `.zip` is unpacked with path checks and the command the Chief named must be a regular file in it; it becomes the tool's only command. Nothing from the file is run during the install. Its entry in `tools.json` is the address, the checksum and the command's name. Resolved by TOOL-002:
  - **Two more fixed operations of the broker carry it**, `toolFetch` (for the ask: download, checksum, size, and every check of an install with nothing written) and `toolInstallLink` (download again, compare, place). The caller sends one https address, the command's name and, for the install, the bot and the sha256; the same worker does the work as the tools user, with the same environment. The tool's name is the command's name.
  - **The address:** https, and every redirect on the way https; no login in it, no `?` or `#` part, and a file name that can be shown as it is (no escaped line break, `/` or direction mark), so that the card shows all of it and nothing else. At most 200 MB, counted as it arrives.
  - **What the file may be** is decided by its first bytes, not its name: an ELF program for the server's processor, a gzip (read as a tar) or a zip. A script, a `.deb`, an `.rpm` and a program for another processor or system are refused. Inside an archive the named command may also be a script, since many tools start through one.
  - **botdot reads the archive itself** (`lib/tools-link.js`, on Node's `zlib`), with no unpacking program: only plain files and folders are written, each as a new file in a new folder under the tool's own `files/`; a link, a special file, an absolute path, a path with `..`, one path twice, more than 20,000 files and folders (those made on the way to a file included) or more than 1 GB unpacked refuses the whole file, and of an archive's modes only "may be run" is kept. The ask makes the same pass without writing, so a file the install would refuse gets no card.
  - **Whose link it is** is read from the Chief chat that asked: the owner's when the exact address stands in a message the owner typed there, the Chief's otherwise, also when a bot wrote it. The owner's no to a tool stands for a week, as for a registry tool, against any link too, also one the owner gives after that no (the owner's answer at the first look, TOOL-007; TOOL-002 had let such a link override the no).
  - **At a later start** a tool from a link is installed again like any other, through the same fetch and comparison; on another kind of processor the file is refused as a program for another processor and the owner is told once.
- **Without the broker there are no installed tools.** On a botdot server that runs without Docker or with separate users off, the Chief's tools answer that tools cannot be installed there.
- **Vocabulary.** An *installed tool* is a command-line program the owner approved for one bot. "Tool" alone stays what a bot may use (`Read`, `Bash`).

## Alternatives

- **System packages through a root operation in the broker.** Covers everything. Rejected by the owner: it reopens a root path, and every package is lost at each update.
- **A bigger image.** Rejected by the owner: every further tool waits for a release.
- **A list of tools maintained in botdot.** Exact and reviewable. Rejected: a tool not on the list waits for a release, which is what this milestone removes.
- **mise with the aqua registry.** It verifies release attestations, the strongest check of the three. Rejected: its binary is 129 MB, and `make` and ffmpeg come through conda there as well.
- **pixi.** The same packages. Rejected: its binary is three times the size and its global installs keep no list of checksums.
- **The server's own user runs the installer.** No new user. Rejected: it would unpack archives from the internet as the user that can read the Vault's key, and root is needed anyway to give a folder to a bot's group.
- **One environment per bot.** Saves 9 MB. Rejected: removing a tool needs a solver run, and a tool's dependencies would put 180 commands on the bot's `PATH`.
- **Tools in the bot's home.** Needs no broker. Rejected: the bot could change what the owner approved.
- **Solve at install time.** Simpler. Rejected: the result could differ from what the card showed, and every reinstall would pay the solver.
- **A bot's `bin` after the system's folders.** Nothing the server has could be replaced. Rejected: a tool that brings a newer `git` would be installed and silently unused.
- **Reading the registry's per-package index directly instead of a dry run.** It would avoid the 630 MB peak. Rejected for now: it was not tried in the trial, and it would put a second resolver next to micromamba's; the peak is once per ask and bounded by running one at a time.
- **A new OK after a restore onto another processor.** Stricter. Rejected: the owner approved the tool and its version, and the files for the other processor are the registry's build of that same version; every tool would wait for a card after such a restore.
- **Checking a tool at start by its files alone.** It starts no program. Rejected: it would not notice a tool that is whole and no longer starts on a new image.
- **The server's own user starts the worker, without the broker.** What the tests do, since they have no root. Not in the product: the image never allows it (`NODE_ENV=production`), and without the broker the Chief's tools answer that tools cannot be installed.
- **A cache on the data folder that stays, shared by every bot's installs.** A second install of a package would need no download. Rejected: the files of different bots' tools would be one file, which is the trial's trap; on a Mac's mount, where no owner is enforced, a bot that changes its tool would change every other bot's and the cache's copy; and the cache would grow without bound in the folder the owner backs up around.
- **Hard links everywhere, with no `--always-copy`.** One way to install. Rejected: on a Linux botdot server the cache would have to move onto the data volume and every bot's files would be linked to it; the first way is what the trial and `tools-real` proved there.
- **Copying the files with botdot's own code where micromamba's copy is refused** (a plain `cp` works on that mount). Rejected: botdot would be writing a conda environment itself (the prefix written into files, the records in `conda-meta`), a second installer next to micromamba.
- **Choosing the way by whether the host is a Mac** (a variable in `compose.mac.yaml`). Rejected: the worker's environment has four fixed names, and what matters is the refusal itself: any data folder that refuses the copy gets the second way, and one that takes it never does.
- **Unpacking a link's archive with `python3` (`tarfile`, `zipfile`), which the image has, or with `tar`.** Less code of botdot's own. Rejected: the image has no `unzip`; Python would be a second language in the installer and its version differs between the image and the machines the tests run on, so the riskiest code would be tested against another unpacker than the one shipped; and with either, botdot would check a list of names and then let another program write them.
- **A plain-http address for the tests' file server.** No certificate in the tests. Rejected: "https only" would then have an exception in the product's code. The tests' file server speaks https with a key and a certificate made anew for each run, which only the tests' installer is given (`BOT_DOT_TOOLS_TEST_CA`, read only where the tests' unprivileged installer is allowed; the broker takes it as a constructor argument that `main()` never passes).

## Consequences

- The image grows by about 20 MB per architecture, and micromamba joins the stack in `AGENTS.md` when this ADR is accepted.
- The broker, the only root code, grows by three operations, and by two more for a tool from a link. Each needs its tests among the privilege tests, which run as root in the hosted workflow.
- botdot trusts conda-forge: it checks that each file is the one the registry's index named when the owner approved, not who built it and not what it does.
- A tool from a link is trusted on the owner's OK alone. An address the Chief proposed may be one a model invented.
- The tools user downloads whatever https address the Chief names, addresses in the server's own network included; what comes back to the Chief is the size, the checksum, the kind of file and a refusal's reason.
- botdot has a tar and a zip reader of its own to keep correct. A zip64 archive, an encrypted zip, a sparse tar entry and every packing but `.tar.gz` and `.zip` are refused rather than read.
- A program from a link that needs another C library than the image's is installed and then does not start: nothing is run at install, so the bot finds out when it runs it. At each start botdot sees that it does not start and installs the same file again, to no avail.
- A large tool is large: ffmpeg is 126 MB to download and about 500 MB on disk, 124 packages. The card shows the download size.
- Resolving can take 630 MB of memory for a moment on a small server.
- The files under `data/tools` are bound to their path. Moving the data folder inside the container breaks them; botdot installs them again from the list.
- On a botdot server hosted on a Mac the data folder is a bind mount, and in the trial that mount showed every file as owned by whoever looked. So "only that bot" and "the bot cannot change its tools" are not relied on there; SECURITY.md says so. Measured on 2026-10-03 on a test server from `compose.mac.yaml` (TOOL-008): the mount enforces neither owner nor mode, a bot's user and another bot's user could both list and write `/data/tools/<bot>`, so there "only that bot" holds by `PATH` alone, as for the bots' workspaces.
- On a botdot server hosted on a Mac every install downloads its packages again: the first way's cache keeps them but its copy is refused, and the second way's cache is removed with each install. A large tool (ffmpeg, 126 MB) is downloaded once for the try that is refused and once for each install after it.
- The second way depends on the words micromamba prints when a copy is refused ("cannot copy: Permission denied" or "Operation not permitted"). A micromamba that words it differently fails the install with that line as its reason, as before this change; `tools-real` runs both ways with the pinned micromamba.
- Each start runs one command of every installed tool as its bot. A tool whose `--version` does something else is run with nobody asking; it runs with that bot's rights and is stopped after ten seconds. The same one command is run when a tool a bot already has is asked for again, by the Chief or by that bot (TOOL-008): "already installed" is said of a tool that starts, and one that is listed and no longer starts is marked missing and can be asked for like a new one.
- The tools user's files are not reachable by the server's user, so the server learns what is in a bot's folder only through the broker and through that bot's own commands.
- Installing needs the registry or the link to be reachable. Everything already installed works without the network.
