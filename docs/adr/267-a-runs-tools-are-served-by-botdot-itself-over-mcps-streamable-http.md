# ADR-267: A run's tools are served by botdot itself over MCP's Streamable HTTP, not by Node processes

- **Status:** Accepted (spec in [#1670](https://github.com/ladrok/bot-dot/issues/1670))
- **Owning task:** [#1670](https://github.com/ladrok/bot-dot/issues/1670)
- **Builds on:** [ADR 014](014-botdots-memory-is-the-only-memory-a-bot-keeps.md) (the private MCP file, `--strict-mcp-config`), [ADR 040](040-a-waiting-message-is-steered-into-the-run-at-its-next-tool-call.md) (the steer hook made the same move, in its amendment), [ADR 047](047-the-chief-uses-connected-apps-in-the-owners-turns-and-every-write-waits-for-an-ok.md), [ADR 062](062-a-message-to-a-busy-bot-starts-beside-the-run-that-is-going.md) (up to three runs of a bot at once), [ADR 266](266-a-bot-can-use-the-owners-own-remote-mcp-servers-through-botdot.md) (the `remote` server)

## Context

Every bot run started, beside `claude`, one Node process for each tool server it had: `vault-mcp.js`, `self-mcp.js`, and when the bot had them `connectors-mcp.js`, `computer-mcp.js` and `custom-mcp.js` (ADR 266). Every Chief turn started `mcp-server.js`, and `connectors-mcp.js` and `custom-mcp.js` when the turn had apps or servers; every Chief look and checkup started `mcp-server.js` too. None of them has logic of its own that needs a process: each reads JSON-RPC on stdin and forwards the tool call to botdot's own HTTP API on 127.0.0.1 with the run's token (`SELF_URL`, `VAULT_URL`, `CONNECTORS_URL`, `BOT_DOT_URL`).

A plain Node process is about 40 to 60 MB resident. Under gVisor that memory is the account's for as long as the run lasts ([#126](https://github.com/ladrok/bot-dot/issues/126)). With up to three runs of a bot at once (ADR 062) and every bot's morning job starting in the same minute, they add hundreds of MB to an account's peak, for code that only relays.

The steer hook went the same way for the same reason (ADR 040's amendment, [#203](https://github.com/ladrok/bot-dot/issues/203), [#206](https://github.com/ladrok/bot-dot/issues/206)): from a Node process a call to an `http` hook that Claude Code makes itself.

## Decision

- **botdot answers the tool servers itself, over MCP's Streamable HTTP.** A run's MCP file names each server as `{ "type": "http", "url": "http://127.0.0.1:<port>/api/mcp/<server>", "headers": { "X-Bot-Dot": "1", "Authorization": "Bearer <token>" } }` where it named `{ command, args, env }`. `<server>` is the name the file already had: `self`, `vault`, `connectors`, `computer` and `remote` for a bot, `botdot`, `connectors` and `remote` for the Chief. No tool server process starts for a bot run, a Chief turn or a Chief look. `--strict-mcp-config`, the private file (ADR 014) and the `mcp__<name>` tool names are as they were.
- **A server is a function of a context.** Each of the six modules (`lib/self-mcp.js`, `vault-mcp.js`, `connectors-mcp.js`, `computer-mcp.js`, `custom-mcp.js`, `mcp-server.js`) exports `create(env)`. `env` holds what the script read from `process.env` (the run's token and URLs, `SELF_*`, `COMPUTER_KIND`, `COMPUTER_SHARED`, `CONNECTOR_APPS`, `CONNECTOR_CALLER`, `BOT_DOT_LOOK`, `BOT_DOT_PAGE`, `BOT_DOT_CARD`, `BOT_DOT_TURN`, `CHIEF_CHAT_ID`…), and the tool list and the descriptions follow it exactly as they did. What a server remembers (the computer is started once, its screen once) is made inside `create`, so each run has its own. `create` returns `handle(message)`, which answers one JSON-RPC message with its response, or with nothing for a notification. `lib/mcp-rpc.js` holds the stdio loop, and each script runs it under `require.main === module`: the many tests that start these scripts over stdio, and `BOT_DOT_MCP=stdio`, keep working with no change.
- **Contexts are found by a token, one per run and server** (`lib/mcp-sessions.js`). It is 24 random bytes, made when the run starts and removed when it ends, as `vaultTokens` are. A token is for one server: the vault's does not open `self`. The first request makes the server from the context; the context keeps its `env` in botdot. A request with no token, an unknown one, one for another server, or one whose run has ended gets **401**; a request through the front door gets 404 (a run's tools are never the owner's request). A bot's own user (ADR 028's separate users) reaches only the tools of its own bot: `server.js` lets the address through for every user on this machine, and the route refuses a token of a context that belongs to another bot, or to the Chief.
- **The Chief's key stays in botdot.** The Chief's config names an address and a token. `BOT_DOT_CHIEF_KEY` and `CHIEF_CHAT_ID` are in the context, from which the tool's calls to botdot's routes take them. The file holds no key, and neither does the process Claude Code starts. Before this, the key was in the MCP file and the environment of `mcp-server.js`.
- **`initialize`, `ping` and `tools/list` answer as JSON.** A notification (a message with no `id`) answers 202 with no body. `GET` and `DELETE` answer 405 with `Allow: POST`: botdot has no stream of its own to send and keeps no session (no `Mcp-Session-Id`).
- **`tools/call` answers as `text/event-stream`**, when the client's `Accept` allows it (Claude Code's does): the headers go out at once, and every 20 seconds (`BOT_DOT_MCP_KEEPALIVE_MS`) a `: keep-alive` comment follows and, when the call carried a `_meta.progressToken` (Claude Code's does), a `notifications/progress` event with that token and a rising `progress`; the one result is sent as a `message` event when the tool ends. A tool may run as long as `MCP_TOOL_TIMEOUT` (15 minutes for a bot, 10 to 15 for a Chief turn, 60 seconds for a look). **The comments are not enough:** Claude Code 2.1.330 and 2.1.331 end a call over HTTP that "sent no response or progress for 300s" (its own words, a tool error), and a comment is neither. A first end-to-end run of this change, with comments only, ended `request_login` at 300 seconds; with the progress notifications the same call ran past 330 seconds and ended with the owner's answer. A client that closes the connection ends nothing else in botdot: the tool runs on to its own end and its answer has nowhere to go. A client that does not accept a stream gets the answer as JSON when the tool is done.
- **The tools do what they did.** They still call botdot's routes with a `fetch` on 127.0.0.1 and the run's token or the Chief's key, so every check on those routes and every answer is unchanged. Only the hop between Claude Code and the tool changes.
- **`BOT_DOT_MCP=stdio` brings the processes back,** as a way back if a version of Claude Code misbehaves with HTTP servers. The MCP file then has `{ command, args, env }` as before, and the routes answer 401 to every token. It is read when a run starts. It is documented in [docs/development.md](../development.md). The test helper starts its servers with `BOT_DOT_MCP=stdio` (below).
- **What is not changed.** The replay's servers (`lib/replay.js`, `replay-computer-mcp.js`, the replay path of `lib/bots.js`) keep their processes. `btw.js` and `dresser.js` start no tool server. The embedding server is another thing. `lib/steer-hook.js` is gone already (ADR 040).

### What changed from the ticket's proposal

- **`remote` is in.** The ticket lists `self`, `vault`, `connectors` and `computer`, and the Chief's `botdot` and `connectors`. ADR 266 added a fifth server, `custom-mcp.js`, for bots and the Chief's owner turns, of the same shape as `connectors`. Left out, every run with one of the owner's remote servers would still start a process, and "no `*-mcp.js` process" would not hold. It moves with the others.
- **The token goes in `Authorization: Bearer`, not in the path.** The ticket does not say where; a token in a header stays out of the access logs of anything that sees the address and is what MCP's own examples use. The address is the same for every run: `/api/mcp/<server>`.
- **The modules keep their bodies as they were, inside `create`, not indented.** A body of 1,000 to 1,600 lines of tool descriptions, some of them in multi-line template literals, would change every line of the diff, and indenting them mechanically changes the text of a template literal that models read. They are left at the left margin, with a comment saying so, and a later change may indent them.
- **The test helper's servers default to `BOT_DOT_MCP=stdio`.** About 95 test files read each server's environment (`rec.self.env.RUN_TOKEN`, `rec.botdot.env.BOT_DOT_LOOK`…) from the MCP file the stand-in Claude is given, to act as the tools do. Those tests are about what the tools do, not how Claude reaches them. The tests of this ADR (`test/mcp-http.test.js`) run servers with the default and cover the file, the route and the lifetime of the tokens.

## Alternatives

- **Keep one stdio process per server.** Nothing to build, and the cost is the one above: hundreds of MB at a busy minute, for a relay. Kept as `BOT_DOT_MCP=stdio`, not as the default.
- **One merged stdio process per run** that serves every server of the run. It saves the memory of all but one process, and keeps the other problems: a process a run owns, its start time under gVisor (about 0.15 to 0.25 s a process, [#203](https://github.com/ladrok/bot-dot/issues/203)), and the Chief's key in its environment. It does not use the move the steer hook already made.
- **Serve the tools from a Unix socket, or an MCP server inside the hook's route.** Claude Code's MCP clients are stdio, HTTP and SSE: a socket would need a process to relay it, and one route for all servers would put every run's tools behind a single token. A route for each server and a token for each run and server is what the rest of botdot's per-run tokens look like.
- **Make the token the path** (`/api/mcp/<token>/<server>`). The same lookup, but the token is in the address of every request and in anything that logs it.

## Consequences

- **A bot run, a Chief turn and a Chief look start no tool server process.** Each saves the resident memory of two to five Node processes (measured on staging after this lands: the follow-up of the ticket) and their start time.
- **The tools run in botdot's own process.** A tool that throws is caught by `handle`, as it was by its own process, and cannot end botdot; but one that holds the event loop (a loop with no `await`) now holds botdot's. None does: they are relays. The computer's screenshots (`computer-mcp.js`) pass through botdot's memory as a string for the length of a call, where they were in another process's.
- **A tool call that outlives its run goes on until it ends by itself.** With a process, the end of the run closed the process, and its calls ended with it. Now the tokens of a run are removed when it ends, so a call that is polling botdot (a login request, a card's answer) is refused on its next poll and ends there; a call that waits on one long request ends when that does. All are bounded by the 14-minute waits they already had.
- **The run's tools need Claude Code to take an HTTP MCP server with headers.** The image pins 2.1.331, and 2.1.330 and 2.1.331 were checked (below); an older one that cannot, or one that behaves otherwise with a long call, is sent back with `BOT_DOT_MCP=stdio`. The 300-second limit of a call that sends nothing is Claude Code's, and may change with it: `test/mcp-http.test.js` checks that the route sends the progress it needs, not that Claude Code counts it.
- **A request through the front door never reaches a tool server,** and `server.js`'s gate lets `/api/mcp/` pass for any user of this machine only so that the route can say 401 or answer: the check of the token is the route's.
- **Not changed for the apps:** nothing in `features`, no new screen, no note in `whats-new/`: nobody sees a difference apart from memory.

## Verified

With the real Claude Code, 2.1.330 (installed here) and 2.1.331 (the image's pin, installed apart for the check), a botdot server started with `BOT_DOT_MCP=http` and the model set to Haiku, from the tests' helper with the real `claude` as `CLAUDE_BIN` (a script kept outside the repository):

- A bot run called `list_jobs` (`self`) and `list_logins` (`vault`) and answered with what they said; the session's transcript shows `mcp__self__list_jobs` and `mcp__vault__list_logins`. A `ps` every 0.7 seconds through the run showed no `lib/*-mcp.js` of this checkout; the same run with `BOT_DOT_MCP=stdio` showed `vault-mcp.js`, `self-mcp.js` and `computer-mcp.js`.
- A Chief turn called `list_bots` (`botdot`) and answered with the id of a bot made for the check, which neither its prompt nor the model could know; its session shows `mcp__botdot__list_bots`.
- A bot's `request_login` (`vault`), which waits for the owner, was left unanswered for 336 seconds, then declined: the run ended as a success with the owner's "declined" as the tool's answer, with `MCP_TOOL_TIMEOUT` at 15 minutes. The same check with `BOT_DOT_MCP=stdio` also lasted 336 seconds. Without progress notifications (the first run of the check) it ended at 300 seconds.
- Claude Code sends `server/discover` (protocol 2026-07-28) before `initialize`, once for each server; the route answers it as it answers any method it does not know (JSON-RPC `-32601`), and Claude Code then goes on with `initialize` and protocol 2025-11-25.

Not checked: the version the ticket names (2.1.316), a run as one of the bots' own users (the broker, on Linux), and memory and processes under gVisor on staging (the ticket's follow-up).
