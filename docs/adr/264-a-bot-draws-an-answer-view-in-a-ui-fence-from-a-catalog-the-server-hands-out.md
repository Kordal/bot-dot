# ADR-264: A bot draws an answer view in a `ui` fence, from a catalog the server hands out

- **Status:** Accepted (by the owner, 2026-11-24, in the grilling of [#1622](https://github.com/Kordal/bot-dot/issues/1622))
- **Owning task:** [#1623](https://github.com/Kordal/bot-dot/issues/1623) (the spec is [#1622](https://github.com/Kordal/bot-dot/issues/1622))
- **Builds on:** [ADR 003](003-one-figure-definition-for-all-apps.md) (what must look the same is data the server hands out), [ADR 004](004-pieces-as-restricted-shape-lists.md) (nothing from Claude is markup), [ADR 071](071-a-page-draws-the-block-kit-bound-to-the-boards-tiles.md) (the block kit), [ADR 113](113-shopping-results-are-product-cards-drawn-from-a-fence-in-the-reply.md) (a fence in a reply read by the apps by rules in a shared fixture)

## Context

A bot answers in Markdown and, at best, a `products` fence or a mermaid diagram. Asked to compare three options, show a time series or gather four values, it writes a wall of text and the owner types the values back by hand. botdot has the parts (fences the apps read, a block kit on pages, cards of questions) but no general way for a bot to build an interface inside its answer. The owner wants charts, tables, forms and more drawn in the conversation, only where they are clearer than text, in the app's own theme, and never at the price of trust: a bot's words are not markup (rule 6), what a number came from is shown, and what the owner taps never approves anything unseen (Milestone 8). This ADR is the format; the apps draw it in later tickets ([#1624](https://github.com/Kordal/bot-dot/issues/1624) and after), and sending the owner's input back is a second ADR with the wave that has inputs.

## Decision

- **An answer view is a ```` ```ui ```` fence in the reply.** The reply stays Markdown the bot writes as before, and an app or a copy that doesn't know the fence shows code. The fence holds one JSON object `{ "alt": "<one line>", "root": <component> }`. A component is `{ "type": "<name>", …props, "children": [<component>] }`: named components, props and children, shaped like A2UI but our own catalog and not bound to its spec; no dependency is added. `alt` is required: what the view says in one line, for a notification, Copy, the quiet line above a fence that can't be drawn, and the bot's and a group member's own reading of it. The stored message keeps the fence.
- **The catalog is data the server hands out** (ADR 003): `lib/ui-catalog.json`, at `GET /api/ui-catalog`, announced as `ui-catalog` in `features`. It holds each component's group, what it means, its props with their kind, length, range, allowed values and whether they are required, its `children` (at most how many, which kinds), the parents it may stand in, whether it is `sourced`, and a `since` number (the catalog `version` it came in); then the `tones` and the `limits`. The page blocks of ADR 071 (hero, kpi, chart, status, callout, table, grid) are its first components, so one renderer can draw both; using the new components on pages is out of scope. Wave 1 is layout, text, data, charts and media (42 components); inputs and actions come in wave 2 and the long tail (calendar, kanban, tree, heatmap, poll, quiz) in wave 3, each wave raising `version` and giving its components that `since`. An app draws what it knows: a component with a `since` past what the app draws is one quiet "unknown" node.
- **The apps validate, as for `products`** (ADR 113): one generic validator driven by the catalog, with no per-component code, in JavaScript for the web page (`public/answer-view.js`) and in the shared Kotlin layer for Android and iOS, run on the same cases (`test/fixtures/ui-cases.json`, a fence in, the normalised tree out or why it is refused). The server route that would hand out a parsed view was rejected for the reason it was in ADR 113: a reply is drawn from its text in many places.
- **What the validator does.** It reads a fence in this order: its size, its JSON, its `alt`, its `root`, then the tree. Past a **limit** the whole fence is refused and drawn as code with its `alt` above it: more than 64 KB (bytes of UTF-8), more than 200 nodes, nesting deeper than 6 (the root is 1), more than 500 points in one chart (the lists a prop marks `counts: "points"`, all series together), and more than 3 `ui` fences in a reply (the others stay code). Everything else is cut or left out, never refused:
  - every string is cut to its catalog length, its whitespace collapsed (a multiline prop keeps its lines); a number is read as its text where a text is wanted, a number as written or as a text of digits, kept inside its range; a list keeps the items it can read, at most its length;
  - **unknown props are dropped**, and no bot sets a colour, size or style: it names a **tone** (`neutral`, `good`, `warn`, `bad`, `accent`) and, in charts, a series by its number; a tone or a value outside a prop's list is read as the prop's default;
  - **an unknown component** (a name the catalog or the app doesn't have, or none) is one quiet `unknown` node, its children unread;
  - **a prop that can't be read cuts only its component**: a required prop that is missing or of the wrong kind turns its component into an `unknown` node, an optional one that can't be read is left out; the view around it is drawn;
  - a child the parent doesn't take (a `tabs` holds `tab`s, an `accordion` `panel`s, a `stat-row` `kpi`s) is left out; containers keep at most their count of children.
  - It returns `problems` too, `{ at, code, prop? }` where `at` is the node's path, so that the server can later tell a bot what it wrote wrong ("a refusal that names what was wrong").
- **Media.** An image, a gallery picture, a link card's picture come from the bot's own files (a path in its workspace: no `..`, no web address, no query, the extension of a picture) or, for an image, from an `https` address botdot fetches itself (ADR 113: the apps never ask the host). A video, audio and a file come from the bot's files only. No embeds, no iframes, no outside video, no SVG. An address that is neither is unreadable, so the picture is cut; a made-up photo address that passes shows the placeholder. Every image and video has a required `alt` of its own.
- **Provenance.** `source` is on every chart, table and KPI (a file, a link, a tile, a tool, or "the bot's estimate"); a missing one is kept as `noSource: true`, which the apps draw as a quiet "No source". A chart's numbers can be read as a table ("Data").
- **A view never approves.** Nothing in the catalog sends, runs or changes anything: no component has a handler, a script, a style or an address that is not `https`. In wave 2 an input or a button only posts the owner's own plain message; it can't approve a card, grant a permission, run a job, change a bot or touch the Board. Approvals stay on cards in Needs you (Milestone 5).
- **Streaming.** A reply being written shows a quiet "Drawing a view…" for a fence not closed yet and draws the view once it closes; a fence never closed stays code once the reply has ended, with its `alt`. The validator's `split` reads a reply this way (text, views, code, drawing) so every place that draws a reply agrees.
- **Where it is drawn** is wherever a bot's or the Chief's reply is drawn (a bot's chat, the Chief's chat, groups and rooms), not in notifications and push (they read `alt`), the Board or pages.
- **The skill** `kit:ui` ([#1625](https://github.com/Kordal/bot-dot/issues/1625)) is on for every bot and the Chief like `kit:shopping`, switched off per bot the same way, and told to each as one line; its rules and its component reference, written from `lib/ui-catalog.json` (`scripts/ui-skill.js`), load only when it is picked. Its eval is `make ui-eval`. The drawing is a later ticket ([#1624](https://github.com/Kordal/bot-dot/issues/1624)), so until it lands a view a bot writes is shown as code.

## Alternatives

- **Show-only first** (a few components and no more), as the advice was. Rejected by the owner: the full catalog, in three waves, the web page first in each and Android right behind it.
- **The server parses the fence and hands out the view**, as pages do (ADR 071). Rejected as ADR 113 did: a reply is drawn from its text in the chat, a draft as it is written, groups, rooms and the document viewer, so a third reader on the server would buy no safety the apps' text-only drawing doesn't already have.
- **Literal A2UI, AG-UI or CopilotKit.** Their spec and a dependency for a catalog we shape ourselves and keep next to our own apps; the shape stays close enough to adopt later.
- **A refusal for any unreadable prop,** so that the bot hears of every slip. A view with one bad prop is far more useful drawn without it than as code; `problems` tells the bot, and only a limit refuses the fence.
- **A colour or size in a prop.** Views would no longer match light and dark, nor the bot's colour; tones do.

## Consequences

- An older app keeps working: it draws what it knows, shows one quiet line for the rest, and asks `features` for `ui-catalog` before drawing a view at all. A newer app on an older server has no catalog and shows the fence as code.
- A component is a catalog entry and a drawing. Adding one raises `version` and gives it that `since`; it is written in `lib/ui-catalog.json`, its drawing in each app, and its cases in the shared fixture.
- Three validators (web, Kotlin for Android and iOS, and the server's own when it checks a view for a bot) must agree; the fixture is what makes them, as for `products`. The Kotlin one is a ticket of its own.
- The validator is generic, so a prop kind it doesn't have (a new media kind, say) is a change to the three of them and an ADR note, not a catalog entry.
- No app draws a view yet (the web page's ticket is [#1624](https://github.com/Kordal/bot-dot/issues/1624)), and a bot is told of the fence only by the skill `kit:ui` ([#1625](https://github.com/Kordal/bot-dot/issues/1625)): with that one merged and no app drawing yet, a view a bot writes is shown as code, so wave 1 is not released to the owner before the web page draws it.
