# ADR-267: Several providers at once, and the model decides which one a run uses

- **Status:** Accepted (spec in [#1664](https://github.com/ladrok/bot-dot/issues/1664)). Supersedes the "one account, one provider" decision of [ADR 255](255-bots-can-run-on-another-model-provider-under-claude-code.md); the model lists of [ADR 256](256-settings-show-the-active-providers-models.md) and the provider form of [ADR 257](257-provider-models-come-from-a-searchable-catalog.md) now show every connected provider, not the active one.
- **Owning task:** [#1664](https://github.com/ladrok/bot-dot/issues/1664)
- **Builds on:** [ADR 255](255-bots-can-run-on-another-model-provider-under-claude-code.md) (a provider is another address under Claude Code), `lib/claude-key.js`, `lib/identity.js` `runAs` (the one place a run's environment is built), `lib/settings.js` (which model a run asks for).

## Context

ADR 255 made the account run on one of three: the subscription, an Anthropic API key or one provider. An owner who has a Claude subscription and DeepSeek and GLM keys could use only one at a time, and switching moved every bot. The owner wants each bot (and the Chief, and the account default) to pick any connected provider's model, and the subscription's, in the same picker.

## Decision

- **Several connections at once.** `claude-key.json` keeps the Claude connection (the subscription, or an Anthropic API key with `use: "api-key"`) and any number of saved providers, at most one per preset (`providers: { <preset>: { … } }`), each key encrypted as before. Saving a provider (`PUT /api/setup/claude/provider`) adds or replaces its entry and picks nothing; `DELETE /api/setup/claude/provider/:preset` removes one. `PUT /api/setup/claude/use` only chooses between the subscription and the API key.
- **The model decides the provider.** A model ID `provider:<preset>:<model>` runs on that saved provider; any other ID, or none, runs on the Claude connection. `claudeKey.routeFor(modelId)` is the one answer to that, and both `settings.args` (which `--model` and `--effort`) and `identity.runAs` (which environment) ask it for the same model, so the arguments and the environment cannot disagree. A model whose provider was removed is no choice: the run falls back to the account default, and to Claude when the default's provider is gone too. Reasoning levels stay per model (`efforts` of each model; the settings `efforts` is their union).
- **The credentials never cross.** A provider run gets `providers.envFor(provider)` (`ANTHROPIC_BASE_URL`, `ANTHROPIC_AUTH_TOKEN`, an empty `ANTHROPIC_API_KEY`, its models) and neither `CLAUDE_CODE_OAUTH_TOKEN` nor an Anthropic key. A Claude run gets the API key or the subscription token and nothing of a provider. One provider's key goes only to that provider's address. `test/provider-mix.test.js` checks this per process with two providers and the subscription running at the same time.
- **Helper calls** (the group router, the notes, an error explained, the memory review) pass `helper: true`; `settings.forHelper` sends them to the provider of the account default model (its small model for the short calls), or to Claude Haiku when the default is a Claude model. A model of a bot is never used for them.
- **API.** `provider-mix` in `features`. `GET /api/setup`: `claude.providers` (all saved ones) and `claude.connection` (`"api-key"` or `"subscription"`); `claude.using` and `claude.provider` still describe what the account default runs on, so an app from before keeps working. Settings: `models` carry `group` and `provider`, `efforts` is the union, `providers` lists the connected ones, `provider` (the older object) describes the account default's provider. `POST /api/settings/refresh-models?catalog` refreshes every provider and Claude. See docs/api.md.
- **A save never switches.** Only a model picked in Settings → Model does. The one exception is the first connection: when Claude can't run (the subscription is signed out and there is no API key) and a provider is saved, the server (`PUT /api/setup/claude/provider`, once for every app, which only redraw) sets its main model as the account default, also over an explicit Claude model that can't run, or nothing could run and setup would wait for a model nobody can pick. A default that already runs on a provider is left.
- **Migration.** An account saved with ADR 255's shape (one `provider`, `use: "provider"`) is read as the new shape on every load and written as it once, when `settings.create` runs: the provider stays saved and the account default becomes its main model (its small one when the default had been a Haiku name). When that account's Claude connection can't run either (the subscription is signed out, as the check at that start says, and no key is in use), the Chief's model and each bot's own Claude name are translated the same way, once: a Haiku name into the small model, any other Claude name into the big one. An older app keeps showing and setting a model: the settings still carry `provider`, and a bare `DELETE /api/setup/claude/provider` removes the default's provider.
- **The apps.** One list in Settings → Model, grouped by provider (Claude's first, then by name) and searchable, on the account default, the Chief and every bot, with the summary line "DeepSeek V4 Pro · DeepSeek · High". The Provider row becomes Providers: the connected ones, "Connect another provider" (the existing form) and Remove for each. No costs or prices anywhere (AGENTS.md rule 5). iOS reads the new fields and ignores them until its Settings catch up (#1355).

## Alternatives

- **A model map per bot** (bot → provider) next to its model. A second control that can disagree with the model; the model's own ID already says where it runs.
- **Keep `use: "provider"` and let a bot override it.** The account default would still be one provider and each bot an exception, with the helper calls having no bot to ask.
- **Translate a Claude name to a provider's model as ADR 255 did.** It hides which provider a bot runs on and cannot work with several; a model's name is its identity.

## Consequences

- A bot that had its own Claude name saved (`opus`, `claude-haiku-5-5`) while the account ran on a provider ran on the provider's model under ADR 255; it now runs on Claude, as its name says. The migration moves such a bot to the provider's model only when Claude can't run (it would fail otherwise); with Claude able to run it keeps its Claude name, and an owner who wants it on the provider picks the provider's model for it.
- `claudeKey.credential()` means the Claude connection only: saving or removing a provider changes no credential, so it no longer clears the usage-limit hold, and signing out of the subscription is decided by the account default's connection. The hold itself is per connection since [ADR 272](272-a-usage-limit-holds-only-the-runs-on-the-connection-that-reached-it.md) ([#1668](https://github.com/ladrok/bot-dot/issues/1668)): a Claude limit holds only the runs on Claude, and a provider's limit only that provider's. Signing out of the subscription is decided by the connection a run uses, not the account default's.
- Each run on a provider still has the quality of that provider's model; the data goes to the provider the owner chose for that bot, and with several that is a per-bot fact the Settings list shows by name.
- The group router uses the account default's provider like the other helper calls; choosing its provider apart is not part of this.
