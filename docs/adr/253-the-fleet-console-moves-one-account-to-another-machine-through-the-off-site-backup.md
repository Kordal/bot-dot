# ADR-253: The fleet console moves one account to another machine through the off-site backup

- **Status:** Accepted (2026-11-16)
- **Owning task:** the owner's request in the project thread "Add Migrate per account in console" (move an account between servers from the fleet console)
- **Builds on:** [ADR 154](154-one-vps-per-customer-a-managed-machine-run-from-a-fleet-console.md) (the console reaches a machine only through its agent and root's request and status files), [ADR 157](157-the-machine-backs-itself-up-off-site-with-restic.md) (each account's parts in the machine's off-site backup), and [ADR 159](159-the-console-turns-a-machines-off-site-backup-on-and-restores-a-machine-from-it.md) (`OFFSITE-RESTORE`, which moves a whole machine). Leaves [ADR 158](158-an-account-is-backed-up-off-site-and-downloaded-on-request.md)'s owner download as it is.

## Context

ADR 159 moves a whole machine: its front door's data and every account, onto a new machine that takes its instance and hostname. An account can only leave a machine by its owner's `.bdb` download and a restore into a fresh account elsewhere (ADR 158), which needs the owner, their passphrase and an upload as large as their data. The console has no way to move one account to another machine (a bigger one, another region, off a machine it shares), and once moved, no way to delete it from the one it left: a managed machine has no admin page.

## Decision

- **Two root requests, root's alone like `OFFSITE-RESTORE`.** One the front door made is refused (`by_root`), each is removed as it is read, and how it went is in a status file named for the account.
- **`IMPORT-<account>` makes the account here from another machine's off-site backup.** Its lines: the other machine's instance (8 hex digits), its repository (empty: this machine's own), that repository's restic password (needed with a repository), and for a Storage Box the sub-account's password once, with which this machine's own SSH key is put on that sub-account (`install-ssh-key`, as `OFFSITE-SET` does) and then forgotten. Root's step takes that instance's latest manifest, refuses a backup of another version than this machine runs (`install version … here first`), one without the account, or one whose front door's or account's parts failed, checks the room as `OFFSITE-RESTORE` does (twice the parts and 512 MB), and restores `front-door/data.tar` and the account's parts (`data.tar`, `env`, each volume's tar) with `restic restore --verify` into `BOT_DOT_DIR/account-import`, each part's size checked against restic's. The front door then makes the account (`front-door.js import-account --account NAME --record -`), from what the other front door kept of it that is no secret: its creation, its login, the terms its owner agreed to and its automatic updates. It gets a user handle of its own and **no passkey and no session**: a passkey is bound to its machine's hostname, so its owner signs in with the sign-in link root already makes (`SIGN-IN-<account>`). It is refused when the name or its login is taken here, on a machine of one account unless it is that one and the machine has none yet, and on a managed machine of several without room for its share. Its data is put back as a set's account is (`restore_account`), with its born stamp, and it runs on this machine's share and instance. It holds the off-site lock. Status: `status/import-<account>.json`, `state` `importing` (with `phase` `download`, `front-door` or `account`), `imported`, `refused` or `failed`, `at`, `account`, `instance`, `snapshot` once found, and `error`. The scratch folder goes however it ends, and an account a failed import made is deleted and erased again, so the import can be asked once more.
- **`DELETE-<account>` deletes the account it left.** The running front door deletes it as the admin page does (`front-door.js delete-account` marks it and waits for that process, which alone holds the rooms: its boat.dev machines, its rooms, its usage, its passkeys, sessions and open sign-in links go, its name is kept as deleted) and root's step erases it from the machine at once, as it erases an account the admin deleted; its off-site snapshots there are forgotten after the usual grace period. Status: `status/delete-<account>.json`, `state` `deleted`, `refused` or `failed`, `at`, `account`, `error`.
- **Both are destructive for the console.** `IMPORT-` carries another machine's repository password and replaces nothing but takes a name; `DELETE-` removes an owner's data. The console's agent sends them only with the operator's passkey over the command, as `import-account` and `delete-account`.
- **A move is these steps, run by the console:** the old machine backs up once more (`OFFSITE`); the new machine, on the same version, imports the account from it (`IMPORT-`); the console gives the operator a sign-in link for it there (`SIGN-IN-`), for its owner; once the owner says it works, the old machine deletes it (`DELETE-`). Writes on the old machine after its last backup are lost, so the console starts the import only after that backup and says so.

## Alternatives

- **The owner's `.bdb` download and restore (ADR 158).** Needs the owner at every step, their passphrase, and an upload of the whole account through a browser; the console could only send links and wait. The owner signs in again on the new machine either way, so the off-site path costs them only the sign-in link.
- **`OFFSITE-RESTORE` of the whole machine.** Replaces the new machine's front door and every account, and takes the old machine's instance: right for a machine's move, wrong for one account.
- **Carry the account's passkeys over.** A passkey is made for one hostname (`RP_ID` is the front door's own), so it would not sign in on another machine's address; they would only be dead records.
- **A per-account repository password.** The machine's repository has one key; giving the new machine the old one's password for one read is what ADR 159's move does already, and the console keeps it sealed.

## Consequences

- The new machine's key stays on the old machine's sub-account until that sub-account goes with its machine (ADR 159's move has the same).
- An account moved to a machine of one account is that machine's account: the console moves one there only when its name is the machine's and it has none yet.
- `import` and `console-refused` are new audit actions.
