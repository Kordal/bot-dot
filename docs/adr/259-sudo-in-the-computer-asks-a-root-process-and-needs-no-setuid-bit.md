# ADR-259: sudo in the computer asks a root process of the computer and needs no setuid bit

- **Status:** Accepted (2026-11-20, the owner's decision on [#1562](https://github.com/Kordal/bot-dot/issues/1562): do not rely on setuid)
- **Amends:** [ADR 035](035-the-account-has-one-computer-all-its-bots-work-on-with-sudo.md) (how its "one user with sudo" is made; the decision that every bot is `box` with passwordless root stays as it was)
- **Builds on:** [ADR 028](028-botdot-serves-several-accounts-on-one-machine-each-walled-off.md) (every container under gVisor in the account's rootless Docker, the account as the wall)
- **Owning task:** [#1562](https://github.com/Kordal/bot-dot/issues/1562)

## Context

Every bot works on the account's computer as `box` and may `sudo apt-get install` (ADR 035). `sudo` is a setuid-root program: it becomes root because the kernel honours the setuid bit of `/usr/bin/sudo`. Under gVisor that is not guaranteed. On a fresh install of 2026-11-20 a bot's `sudo apt-get install cowsay` failed with "effective uid is not 0, is /usr/bin/sudo on a file system with the 'nosuid' option set": the container's root file system is a 9p/directfs mount (`runsc`, `--overlay2=none`, ADR 028), the mount ignores setuid, and nothing in the computer can change that. The same failure had come on hq on 16 November, when an apt upgrade of the host moved `runsc` between two releases. Both times the computer's files, mounts and capabilities were fine; only the one mechanism sudo needs was gone, and `docker exec` was the only thing in the computer that could still start a process as root.

Setuid is a property of the host's `runsc` release and its mount options, which botdot does not build and cannot test against each one. A computer whose purpose is that bots install programs cannot depend on it.

## Decision

The computer's `sudo` becomes a client of a root process of the computer. Nothing in it relies on a file's setuid bit.

- **`botdot-sudod`** (`deploy/desktop/botdot-sudod`) is one Python process, started by botdot with `docker exec -u root` at each start of the computer, and left running. It listens on `/run/botdot-sudo/sudo.sock`. A client sends the command, its environment and its own stdin, stdout and stderr as passed file descriptors (`SCM_RIGHTS`). The helper runs the command as the user asked for (root by default; `-u` and `-g` work), with those descriptors, in its own session, passes on the signals the client received, ends the command if the client goes away, and answers with the exit code.
- **The one check is who asks.** The helper reads the user id of the process at the other end of the socket (`SO_PEERCRED`) and serves `box` and root only. The browser user, which Camoufox and botdot's bridge run as (ADR 035), is refused, as are all the computer's other users. No password and no sudoers file: that is what "passwordless sudo" was already.
- **`/usr/local/bin/sudo`** (`deploy/desktop/botdot-sudo`) is the client, and the only `sudo` the image has (the `sudo` package is no longer installed, and the sudoers file is gone). It reads sudo's options as far as the computer uses them (`-n -E -H -S -u -g -D -s -i -l -v -k --`, `VAR=value`), keeps what `env_reset` keeps and gives the command sudo's `secure_path`, `HOME` of the target user and `SUDO_USER`, `SUDO_UID` and `SUDO_GID`. Run as root already, it runs the command itself. Everything that already says `sudo`, a bot's `sudo apt-get install -y NAME`, botdot's `sudo -n …` in `lib/storage.js` and `botdot-tailscale`'s start as root, works as before.
- **Files come in with each start.** botdot copies both files into the computer at every start (`syncScripts`), as it already does for the browser launcher and `botdot-tailscale`, and runs `botdot-sudod --ensure`. So a computer made before this gets them without a reset, a helper that died is started again, and one of an older build is told to end once its own commands do and is replaced. When it starts a computer that was off, botdot also asks `sudo -n true` as `box` once and logs what sudo said if it fails. A computer whose helper does not start still starts; what needs no root works, and `sudo` says plainly that the helper does not answer.
- **`box` stays the bots' user.** Nothing the bots or the desktop do changes: the files of `/home/box` and `/workspace` keep their owner, Camoufox and the screens run as before, `botdot-install` still puts its programs into the home, and the identity check of botdot's own server (ADR 028), which looks at the users of sockets on botdot's machine and not in the computer, is not touched.
- **For the bots,** the prompt says what is true again: `sudo apt-get install -y NAME` installs system-wide with no password and is lost with an update of the computer; `botdot-install` and `~/.local/bin` install into the home and stay. The words of [#1563](https://github.com/Kordal/bot-dot/pull/1563) that sudo cannot work, and the hint that its failed output carried, are removed.

## Why root in the sandbox is acceptable

It is not a new privilege. ADR 035 gave every bot passwordless root in the computer, knowing that every bot can then see and change everything there, and the owner chose it. This decision changes the mechanism by which they get it, not who gets it or what it reaches. A bot that could run anything as root through `sudo` can run anything as root through the helper, and nothing else can.

What keeps root harmless outside the computer is unchanged and does not rest on setuid:

- **gVisor is the boundary.** Root in a gVisor sandbox is root of its own Sentry and file system view, not of the host kernel. The computer has Docker's default capabilities, no `--privileged`, no `NET_ADMIN` and no host mount but its own volumes (ADR 035), and botdot's firewall is set from outside by a `docker exec --privileged` (ADR 034), which root in the computer cannot undo.
- **The host mapping is rootless.** The computer runs in the account's own rootless Docker (ADR 028): container root is the account's unprivileged Linux user on the host, which owns nothing of another account's, of botdot's own machine or of the front door's. Another account, the botdot server and the machine stay out of reach, as before.
- **The walls between accounts are the Linux users and their rootless Dockers**, not a user inside a computer. Nothing here touches them.

## Alternatives

- **Run the bots' shell as root by default** (`docker exec -u root`, no sudo needed, which is also what the owner proposed first). It works with no helper, but every file a bot makes in `/home/box` and `/workspace` would be root's, and the desktop (XFCE, the computer-server, `start_program`), which runs as `box`, could no longer write its configuration or a bot's files; the screens and Camoufox's Downloads folder would need their owners put right after each command. Some tools refuse or behave differently as root (a browser's sandbox, Puppeteer), and `botdot-install` and every tool that writes to `~` would put root-owned files in the volume the bots share. It also gives up `box` as the line between a bot's ordinary work and root, which the prompt, `botdot-run` and the sweep (ADR 131) all use. Rejected as the more invasive of the two.
- **Give `/usr/bin/sudo` a setuid-honouring mount** (a tmpfs with `suid`, a bind mount). It depends on a `runsc` flag or release behaviour botdot cannot test, which is the dependence this ADR removes.
- **A file capability on a helper binary.** It rests on the same mount honouring a property of a file that the host's `runsc` decides, which botdot cannot test.
- **Keep the real sudo and the sudoers file, with the helper as a fallback.** Two ways to root, one of them half-working and printing the "nosuid" error that sent the owner looking for a cause.
- **Steer the bots to `botdot-install` and say that sudo cannot work** ([#1563](https://github.com/Kordal/bot-dot/pull/1563)). It left a program only apt has impossible to install on the computer, and told the owner's bots a limit the product should not have.

## Consequences

- **`sudo` and `apt` work on every account's computer whatever the `runsc` release does with setuid.** The check at each start no longer blames `runsc`, since nothing relies on its setuid.
- **A new root process in the computer** that a bug could turn into a way for a user other than `box` to reach root. It answers only `box` and root by their peer user id, runs nothing of its own accord, takes no command from a file, and has a test that a refused user runs nothing. Its code is one file of botdot's, copied in at each start; a bot with root could replace it, as it could replace every other script of botdot's there, and botdot's copy comes back at the next start (ADR 035).
- **`sudo` is not the real sudo.** A command that uses a feature the client does not read (sudoedit, `-A`, a password prompt, plugins) fails with sudo's own kind of message. The ones the bots and botdot use are tested. No terminal is passed as a controlling terminal: a command gets the caller's descriptors and no tty of its own, so a program that opens `/dev/tty` itself fails.
- **Commands run as root now belong to the helper, not to a bot's command.** `botdot-run` ends what a bot's command started as `box` and has always left root's processes alone (ADR 131, a daemon of the computer's Tailscale); the signals of a command that ran out of time go through the client to its root command, and one whose client is killed outright is ended by the helper.
- **Not checked on a real gVisor host.** The tests run the client and the helper on Linux (and skip elsewhere); the descriptor passing, `SO_PEERCRED` and the process group handling are plain Linux behaviour that gVisor documents as supported, and the extra step of `tests/integration/gvisor-real.js` asserts them on the real thing. That step needs Docker and the network; whoever merges this should read its first run.
- **Amends ADR 035** only in how its sudo is made: the "Every bot has root … through sudo" and "passwordless `box ALL=(ALL:ALL) NOPASSWD: ALL`" lines now mean the helper, and the container still has Docker's default capabilities, without `--cap-drop ALL` and without `no-new-privileges`, which root in it needs.
