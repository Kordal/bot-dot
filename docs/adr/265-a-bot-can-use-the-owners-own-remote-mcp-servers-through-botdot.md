# ADR-265: A bot can use the owner's own remote MCP servers, through botdot

- **Status:** Accepted (spec in [#1636](https://github.com/ladrok/bot-dot/issues/1636))
- **Owning task:** [#1636](https://github.com/ladrok/bot-dot/issues/1636)
- **Builds on:** [ADR 010](010-a-connected-app-action-waits-in-its-run.md) (an action waits in its run), [ADR 014](014-botdots-memory-is-the-only-memory-a-bot-keeps.md), [ADR 047](047-the-chief-uses-connected-apps-in-the-owners-turns-and-every-write-waits-for-an-ok.md) (the Chief's turns), [ADR 102](102-a-replay-reads-in-connected-apps-and-with-saved-logins.md) (replays), [ADR 168](168-a-missing-app-is-one-connect-card-and-connecting-it-carries-the-work-on.md) (a missing app is one card), [ADR 174](174-an-app-can-have-several-accounts-and-each-bot-uses-one.md), [ADR 184](184-an-action-that-reaches-no-one-can-be-always-allowed-for-every-bot.md), [ADR 220](220-a-series-of-one-app-action-asks-on-one-card.md), [ADR 221](221-a-bot-sees-every-account-of-its-apps-and-names-the-one-it-acts-through.md), [ADR 231](231-every-bot-has-every-connected-app-and-the-owner-only-takes-one-away.md) (reach)

## Context

Connected apps come only through Composio. An owner who runs an MCP server of their own (a company tool, a notes server, Linear, a home server) has no way to give it to a bot, and handing a bot the server's address and key in its own MCP config would put the key where the bot and the AI can read it. botdot already has what makes an app safe for a bot: the call is made by the server, the key never reaches the run, a write waits on a card for the owner's yes, a replay does not write, and a look has no apps. A remote MCP server should get exactly those.

## Decision

- **botdot is the MCP client, the bot never is.** `lib/mcp-client.js` speaks the MCP Streamable HTTP transport (`initialize`, `notifications/initialized`, `tools/list`, `tools/call`; the `Mcp-Session-Id` and `MCP-Protocol-Version` headers; JSON or `text/event-stream` answers; `DELETE` of the session) with Node 22 built-ins only. A session lasts one operation. A server's tools list is cached for five minutes. No OAuth and no stdio servers in this version (follow-ups).
- **The owner adds a server on the Apps page** (web and Android): a name, an `https://` address and, if it needs one, a key. botdot checks it (an `initialize` and a `tools/list`) before keeping it, so a wrong address or key is refused with words. Up to 20 servers. Routes: `/api/connectors/servers` (`custom-mcp-servers` in `features`).
- **The key is a secret** ([ADR 014](014-botdots-memory-is-the-only-memory-a-bot-keeps.md) and the Vault): it is encrypted with the Vault's key in `data/custom-mcp.json` (mode 0600), sent only as one header (`Authorization: Bearer` by default, or a header the owner names) of botdot's own request, and never in a bot's MCP config, environment, argv, a log, a chat or any API answer (an answer says `hasKey` only). Every error and every tool answer is scrubbed of it, also in the shapes it could be echoed in.
- **A bot meets a server like a connected app.** A server is an "app" with the slug `mcp-<8 hex>` in `lib/connector-approvals.js`, so its grants, cards, "Allow once / always", the 14-minute wait ([ADR 010](010-a-connected-app-action-waits-in-its-run.md)) and the late-yes carry-on ([ADR 168](168-a-missing-app-is-one-connect-card-and-connecting-it-carries-the-work-on.md)) are the ones that exist. The run gets a small relay (`lib/custom-mcp.js`, stdio, only POSTs to botdot with its run token) with **two meta tools**, `remote_tools { server, search?, tool? }` and `remote_call { server, tool, arguments }`, rather than one tool per remote tool: a server's tools change, may be many, and need no change to a bot's tool list.
- **What goes at once and what waits.** A tool whose `readOnlyHint` annotation is `true` and that does not also say `destructiveHint: true` goes at once. Every other tool, with no annotation or with any other, waits on a card that shows the call in full. The annotations are the server's own claim (the MCP spec says so), so a server that lies about `readOnlyHint` is trusted by the owner who added it; the choice of the owner to add it is the trust.
- **Reach** ([ADR 231](231-every-bot-has-every-connected-app-and-the-owner-only-takes-one-away.md)): every bot has every server unless the owner took it away (`botsOff` in the server's record, set on the Apps page). The Chief has all servers in the owner's turns ([ADR 047](047-the-chief-uses-connected-apps-in-the-owners-turns-and-every-write-waits-for-an-ok.md)); a look (a read-only Chief session) has none; a replay ([ADR 102](102-a-replay-reads-in-connected-apps-and-with-saved-logins.md)) reads for real and a write is answered "not done" without calling the server. What a Chief turn reads from a remote server counts as outside content (it can't be trusted to instruct), as a web page does.
- **Approvals.** A lasting "always allow" on a server's tool is kept as for an app. "Always allow for every bot" ([ADR 184](184-an-action-that-reaches-no-one-can-be-always-allowed-for-every-bot.md)) is not offered for a server: what it reaches is unknown to botdot. A series of calls ([ADR 220](220-a-series-of-one-app-action-asks-on-one-card.md)) is not offered either in this version. Removing a server removes its grants.
- **The Chief proposes, the owner types the key.** The Chief can list the servers (`list_mcp_servers`) and offer one (`offer_mcp_server`: a name and an address, never a key): it shows as a card in Needs you that opens the Apps page, where the web form is filled in; the owner adds it there. A yes on the card only closes it. A key is never asked for in a chat.
- **Which addresses botdot will call.** Only `https://`, with no user-info, no query string and no fragment; not `localhost`, `*.local`, `*.internal`, or a one-label name; no IP literal in a private, loopback, link-local, carrier-grade, multicast or reserved range (IPv4 and IPv6, including IPv4-mapped, NAT64 and 6to4 forms). The check runs again on **every connection** through the DNS `lookup` of the request itself, so a name that resolves to a private address, or changes to one after the first look, is refused (no DNS rebinding). No redirect is followed (a redirect to another address would escape the check). An answer is read to at most 8 MB, and at most 500 tools of a server are kept; an answer shown to the bot is cut at 40,000 characters. A test-only environment variable, `BOT_DOT_MCP_ALLOW_LOCAL=1`, lets the tests use a server on localhost; it is not documented to owners.

## Alternatives

- **Put the server in the bot's own MCP config** with its key in a header. The key would be readable by the bot and the AI, and approvals would not be botdot's. Rejected.
- **One tool per remote tool**, mirrored into the bot's tool list. More faithful to what Claude's own MCP client would show, but the tool set changes with the server, a run's tools are fixed when it starts, and every name must be made safe and unique. The two meta tools keep the run's configuration constant.
- **Trust the annotations less** (every call waits) or **more** (none waits). Every call waiting makes read-only servers useless; none waiting ignores that writes exist. The annotation is the one signal the protocol gives; unknown means waits.
- **Queries and user-info in the address**, which some servers use for a key. Refused: a key in an address is shown in a log, a card and a chat. The key has a field of its own.
- **OAuth and stdio servers.** Larger, with their own risks (a local process, a browser sign-in); follow-ups.

## Consequences

- A server's key and tools stay on botdot's side; a bot sees only names, descriptions and results.
- A server that lies about `readOnlyHint` can write without a card. The owner chose it, and the card for everything else still shows in full.
- Tool names a bot gets are the server's own; they are text from a third party, so the bot is told they are not instructions and a Chief turn counts them as outside content.
- Android has no prefill from the Chief's card (the card opens the Apps page; the form is typed). iOS follows later in the catch-up of Android's and the web page's features.
