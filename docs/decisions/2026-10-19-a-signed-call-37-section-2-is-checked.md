2026-10-19: A signed call (#37, section 2) is checked by the account's botdot server, not the front door: it reads the body already and holds the job's secret, which an HMAC check needs itself (a hash is not enough), kept like a notify secret, in the Vault for the owner and encrypted with the Vault's key in `data/call-secrets.json` (`notify.secretStore` with another file), so the front door keeps no account's secrets and only passes `X-Botdot-Signature-256`, `X-Botdot-Timestamp` and `X-Hub-Signature-256` on and slows down the `401`s as wrong keys. The mode is a field of the job's approved definition (`callMode: "signed"`, absent for a key), so turning it on or switching it waits on the same card as a call and each yes makes a new key or secret. Two forms, both under one secret: botdot's own (`X-Botdot-Signature-256` over `<X-Botdot-Timestamp>.<body>`, five minutes either way, as its notifications) and GitHub's (`X-Hub-Signature-256` over the body, no time); every signature is taken once (`data/call-signatures.json`, a day, the last thousand of a job), which stops a replay of either form for that long, and one whose call started nothing is given back. Rejected: Stripe's own `Stripe-Signature: t=…,v1=…` header (a third form for the same check; botdot's form is Stripe's scheme already), deduplicating on `X-GitHub-Delivery` (not signed, so a replayer changes it), keeping signatures forever (a GitHub-style sender whose body never changes could call once only; that sender uses the timestamped form), and checking at the front door (it would need every account's secrets).
