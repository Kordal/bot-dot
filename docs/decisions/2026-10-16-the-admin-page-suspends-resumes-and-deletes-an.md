2026-10-16: The admin page suspends, resumes and deletes an account through the same request folder and root's step as a new account, with no word of what to do in the request: the front door changes its own data (`suspended` on the account, or the account removed and its name kept in `deleted`), writes the empty file named as the account, and root's step reads what that data says of the account (`running`, `suspended`, `deleted`, or nothing when the data has no such account or can't be read) and makes the machine match, removing the request once that is done and then reading the data once more: the front door changes its data before it writes the request, so a change whose request found the old one still there (and was dropped as already asked) is read then, and a later one is a request of its own. It erases an account only on an explicit `deleted`, and never the admin's own, so a missing or broken `front-door.json` erases nothing. Suspend stops the account's whole rootless Docker (`systemctl disable --now botdot-account@<name>`, or without systemd a `SIGTERM` to its `dockerd`), which stops its containers itself and starts again the ones it should when it starts, so resume is the install's own `account` step; delete stops it the same way, then removes its home (its data and Docker's storage), socket folder, runtime folder, Linux user and group, and its `/etc/subuid` and `/etc/subgid` lines. An update of the install leaves a suspended account stopped. Rejected: an action word in the file (more for root's step to parse, and two requests for one account could disagree), and a `compose stop` of its containers (a computer stopped by hand doesn't come back as it was).
