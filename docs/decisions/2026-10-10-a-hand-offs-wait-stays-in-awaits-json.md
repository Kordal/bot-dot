2026-10-10: A hand-off's wait stays in `awaits.json` until its follow-up has started (its run is on record), not only until it is queued, because a queued follow-up whose start failed as its turn came left the queue with its wait already gone, and the hand-off never came back. A follow-up whose start fails, from the queue or at once, is logged and queued again from its wait on the next pass (after each run's end, each answer and every 30 seconds), with no limit, and the bot's face keeps showing that it waits until it starts. A queued follow-up starts with its wait as it is then (`forFollowUp` in `lib/awaits.js`), not the copy it was queued with: a later answer, or a teammate of the same run that ended meanwhile, goes along in that one follow-up, and the copy is only read for a follow-up an older botdot queued after settling its wait. This replaces #308's joining of a later wait into the queued follow-up. As it starts, the wait is done with the teammates that follow-up was told of; a teammate asked after it was queued and still at work is left out and keeps the wait, for a follow-up of its own. While the wait stays, a teammate's later message in that exchange is taken as an answer, as it is before the wait is over. If `awaits.json` can't be saved as the follow-up starts, the wait is gone from memory and only logged; a restart before the next save of that file starts the follow-up once more. Rejected: putting the failed item back in the queue (the next start would likely fail at once, and the item would have to be kept current with every later answer); a failed run in the bot's chat, or a limit on attempts (nothing asked for either).
