2026-11-25: The twelve biggest installer test files (`installer.test.js`, `installer-offsite`, `-managed`, `-update`, `-accounts`, `-switch`, `-named`, `-provisioning`, `-backup`, `-feedback`, `-distros`, `-suspend`) are cut at test boundaries into 45 parts (`test/installer-<topic>-<n>.test.js`; `installer.test.js` became `installer-install-<n>`) of about 170 test seconds each, as the tests took in CI, because `node --test` runs the tests of one file one after another and each shard of `server-tests` ended with its longest file (run 45578904352: the four shards took 13:19, 7:48, 7:57 and 8:10, and each one's time was its longest installer file plus about 50 s: `installer-offsite` 734 s, `installer.test.js` 426 s, `installer-managed` 414 s, `installer-update` 401 s), so no number of machines could go below that file. The tests moved unchanged (235 before, 235 after, each one's text identical, checked by parsing the old and the new files); a helper that two parts of a topic share and that is longer than about 25 lines went to `test/installer-<topic>-helpers.js` (offsite, switch, backup), a shorter one is written in each part that uses it, and the common setup stays in `test/installer-helpers.js`. The seven files under about three minutes (`-disk`, `-embed`, `-keys`, `-links`, `-moved`, `-ram`, `-ready`) stay whole. The file names still start with `installer`, so `BOT_DOT_SKIP_INSTALLER_TESTS`, `INSTALLER_PATHS` (`^test/installer.*\.js$`) and `test/ci-installer-filter.test.js` need no change. The cut is by the seconds the tests took in a shard (run 45626200722, on six machines), not by their number: a part of 34 quick tests took 433 s there and held its shard back, where the first cut by the times of the four-machine run had put it at 145 s, so a part is cut again by the seconds of the latest run when it passes about 200. Splitting alone was not enough: with four machines the shards took 8:16, 6:47, 8:18 and 6:50 (run 45624390508), each now following its total installer seconds, since the 4 vCPUs of a machine were full (the shard with 1,750 installer seconds took 6.5 minutes, the one with 2,390 took 8.2); the six machines of [2026-11-25](2026-11-25-the-server-tests-run-on-six-machines.md) go with this. The parts of a topic sit next to each other in the file list and `--test-shard` gives file number N to shard N mod M, so the parts of one topic land on different shards by themselves, and no name was picked to tune the load, because a new installer file shifts every later one by a shard. Replaces the rejection of splitting in [2026-11-23](2026-11-23-pr-skips-installer-tests.md), which was written for the skip (the skip stays as it was). Rejected: only more machines (a shard cannot be shorter than its longest file), fewer files at once per machine (the same work on the same cores), and a daily run of the installer tests alone (a break would be found a day later, by someone else's pull request).
