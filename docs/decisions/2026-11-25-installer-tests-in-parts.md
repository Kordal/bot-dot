2026-11-25: The ten big installer test files (`installer.test.js`, `installer-offsite`, `-managed`, `-update`, `-accounts`, `-switch`, `-named`, `-provisioning`, `-backup`, `-feedback`) are cut at test boundaries into 30 parts of at most about three minutes each in CI (`test/installer-<topic>-<n>.test.js`; `installer.test.js` became `installer-install-<n>`), because `node --test` runs the tests of one file one after another and each shard of `server-tests` ended with its longest file (measured in run 45578904352: the shards took 13.1, 7.6, 7.8 and 8.0 minutes, and each wall time was its longest installer file plus about 50 s: `installer-offsite` 734 s, `installer.test.js` 426 s, `installer-managed` 414 s, `installer-update` 401 s), so no number of machines could go below that file. The tests moved unchanged (219 before, 219 after, each one's text identical); a helper that two parts of a topic share and that is longer than about 25 lines went to `test/installer-<topic>-helpers.js` (offsite, switch, named, backup), a shorter one is written in each part that uses it, and the common setup stays in `test/installer-helpers.js`. The file names still start with `installer`, so `BOT_DOT_SKIP_INSTALLER_TESTS`, `INSTALLER_PATHS` (`^test/installer.*\.js$`) and `test/ci-installer-filter.test.js` need no change. The parts of a topic sit next to each other in the file list and `--test-shard` gives file number N to shard N mod 4, so the parts of one topic land on different shards by themselves; by the file names the four shards get 980 to 1,280 test seconds of installer tests, and no name was picked to tune that, because any new test file anywhere shifts every later file by one shard. A part is cut where a topic's sections or helpers begin, and by the measured seconds of its tests; when a part grows past three minutes, cut it again the same way. Replaces the rejection of splitting in [2026-11-23](2026-11-23-pr-skips-installer-tests.md) (which was written for the case of skipping; the skip stays as it was). Rejected: more machines (a shard cannot be shorter than its longest file, and the installer tests are CPU-heavy on a 4-core machine, so each machine's share does not shrink in proportion), fewer files at once per machine (the same work on the same cores), and a daily run of the installer tests alone (a break would be found a day later, by someone else's pull request).
