2026-10-18: A bot uses an SSH key of the owner's Bitwarden only through `run_with_ssh_key`: botdot starts an ssh-agent as the bot user in the bot's computer (`ssh-agent -D`, so the listening program is the one whose pid botdot holds), loads the key into it as root with its own copy of `deploy/desktop/botdot-ssh-add` (key on stdin; sent only after `SO_PEERCRED` shows that pid and the bot user, through a socket of root's own that it relays, because the agent's folder is the bot's and the bot could put a socket of its own there), runs the one command with `SSH_AUTH_SOCK`, and ends the agent; the agent makes itself untraceable and root's processes are closed to the bot (`--cap-drop ALL`), so the bot can sign with the key and cannot read it. Sharing the key with the bot is the only gate, with no switch like `inComputer`, because that switch exists for a secret the bot can read. A bot it is not shared with sees its name and type, `shared: false`, as it sees every other entry (the line above), and not its fingerprint or public key. The desktop image gets `openssh-client`. Rejected: the key in the command's environment or a file, as `run_with_login` does (the bot reads it), ssh-add run as the bot (its stdin and memory are the bot's to read), an agent that stays up between commands (it would sign for any program of the bot's at any time), and an SSH key in botdot's own vault (the issue asks for Bitwarden's SSH key items). ([#44](https://github.com/Kordal/bot-dot/issues/44))
