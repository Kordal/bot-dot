2026-11-06: A managed machine (ADR 154) takes the security updates of Docker's own packages by itself: at every install and update the installer writes `/etc/apt/apt.conf.d/51botdot-docker` (`Unattended-Upgrade::Origins-Pattern { "origin=Docker,label=Docker CE"; };`) and `/etc/apt/preferences.d/botdot-docker`, which keeps each of docker-ce, docker-ce-cli, docker-ce-rootless-extras, containerd.io and the compose and buildx plugins that is installed on the major version it has (`Pin: version 5:29.*`, priority 990, which never downgrades), each file written only when it changes, once the install's answers are checked (a run refused for a machine that isn't managed, or one on this computer only, writes neither), and both removed by the uninstaller; the origin is written only beside the pin, so the fleet console's cloud-init, which installs a pinned botdot release that can predate the pin, writes none of its own, because get.docker.com installs them from download.docker.com, which Ubuntu's stock origins leave out, and a managed machine has no admin to run apt, so fixes to runc, containerd and dockerd never arrived. What such an upgrade does to running accounts, from the installer's own settings: the machine's Docker has no `live-restore` (its daemon.json holds only the log limits), so the restart of `docker.service` by docker-ce's package stops the front door and Caddy, which `restart: unless-stopped` brings back within seconds, as an install's own restart of that Docker does; an upgrade of containerd.io restarts `containerd.service`, under which running containers' shims go on; each account's rootless Docker is a unit of its own (`botdot-account@<name>`, with its own containerd), which no Docker package restarts, so its botdot server and computers go on with the binaries they started with and take the new ones at that unit's next start (a reboot, an update's switch); and runsc, every account's sandbox, is gVisor's package and stays pinned (2026-11-06-gvisor-comes-at-one-release). That is acceptable: a few seconds without the front door at the hour unattended-upgrades picks is what an update of botdot costs too, and it closes holes in the root containers that face the internet (the front door, Caddy), whose escape is root on the machine. A new major is not: it can change defaults and drop what botdot relies on, and every machine would take it the same morning rather than one at a time, so it comes only with a botdot change. A machine that isn't managed, or whose Docker is Ubuntu's docker.io (already in the stock origins), keeps its own policy. Not checked on a real Ubuntu 24.04 with Docker's packages: the restart in docker-ce's package scripts, and whether needrestart, which unattended-upgrades runs, restarts an account's unit because its rootless Docker runs a replaced binary (that account's containers would then restart once, as at its switch). Rejected: no pin (a new major on the whole fleet at once), `apt-mark hold` (no fixes at all), and a major written in the installer like `GVISOR_RELEASE` (a machine to which get.docker.com gave a newer major would get no update at all, as apt never downgrades it and takes nothing above the pin).
