2026-10-19: A job's notify address (#37, section 1) is a field of the job's approved definition (`notifyUrl`), so it waits on the same card as any change and its proposal is taken back by turning it off; a new address waits for the owner's yes whoever asks, the owner's own edit too, since the yes is what makes the secret. Only `https://` to a public host: the host is checked when proposed and again after DNS at each send, the checked address is the one connected to (`lib/network-address.js`, as `vault-http.js` does), and no redirect is followed at all. The signature is `X-Botdot-Signature-256: sha256=<hex>` over `<X-Botdot-Timestamp>.<body>` (Stripe's scheme with GitHub's header shape), so a receiver rejects replays by the timestamp. The secret is in the Vault for the owner and, encrypted with the Vault's key, in `data/notify-secrets.json` for signing, so a locked Bitwarden does not stop notifications; a new address keeps the secret. 5 s a try, two retries after 1 s and 4 s on no answer, 5xx, 408 and 429; never on another 4xx. A script that found nothing is told too (`status: "quiet"`, no `runId`), since the owner asked to hear each run's end. Tests reach a receiver on 127.0.0.1 only with `BOT_DOT_NOTIFY_LOCAL=1`, as `BOT_DOT_PUSH_HTTP` does for Web Push. Rejected: reading the secret from the Vault at each send (a locked Bitwarden would drop notifications), `http://` to public hosts (the reply would travel readable), following redirects to public addresses (a second check for little use), and a control in the apps (rule 5: the Chief does it by chat).
