2026-11-25: the viewer's paste offers the owner's text and presses Ctrl+V 250 ms later ([#1734](https://github.com/ladrok/bot-dot/issues/1734), ADR 279): RFB's extended clipboard is a round trip (the computer is told, asks, is handed the text), and a key sent at once pastes what the computer had; noVNC gives no signal when the text has arrived. Rejected: pressing the key at once, and a clipboard panel to paste into first. Where the computer has no extended clipboard, noVNC sends Latin-1 only (other letters become "?"), so "Type it", which sends each letter as its own key, is the way for Polish text there. Also, before the Ctrl+V the viewer's paste releases the keys noVNC has down for a held ⌘, which on a Mac are Alt_L (left ⌘) and Super_L (right ⌘), not the Super keys, because noVNC's keyboard (`core/input/keyboard.js`) shuffles them for the computer, and Alt left down makes the computer see Alt+Ctrl+V ([#1734](https://github.com/ladrok/bot-dot/issues/1734)). It asks noVNC's own `isMac()`/`isIOS()`, as the keyboard does, instead of reading its private list of keys held. It puts back what the owner still holds after the V (a Ctrl is not released, a ⌘ is pressed again, with the same keys), because noVNC's keyboard still has them down and would send the owner's next key without them. Only the platform's own paste keys are held back (⌘+V on a Mac, Ctrl+V elsewhere, by the same `isMac()`/`isIOS()`): Ctrl+V on a Mac and Super+V elsewhere go through noVNC as the keys they are. A held-back paste that finds no text in the owner's clipboard (an image), or whose paste event does not come within 100 ms, sends the computer a plain Ctrl+V, with the same holding of what the owner has down, so the keys are never lost.
